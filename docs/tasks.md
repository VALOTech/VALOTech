## How to use this document

Tasks are grouped by feature code and carry a stable id `<CODE>/T<N>`. A task lives in exactly one section, owned by one feature; work spanning features is split. `Evidence:` is a commit sha, a test name, or `path:Symbol` — never a bare line number, which moves.

| Marker | State | Required |
|---|---|---|
| `- [ ]` | open | — |
| `- [~]` | in progress | `Note:` — what is done and what is left |
| `- [!]` | blocked | `Blocked by:` — a task code or a register anchor |
| `- [x]` | closed | `Evidence:` |

**Open `REVIEW` rows are drained before other roadmap work.**

- [ ] I18N-001/T5 — The ecosystem glossary: one answer per technical term per locale, harvested from the siblings rather than minted here

A survey of all seven sibling repositories is done and its findings bound the work. **No blanket rule survives three terms**: `hi/bn/ur` keep `AI` and reject `cookie`; `es/fr/pt/de/ru/ar` keep `cookie` and reject `AI`, which is `IA`, `KI`, `ИИ` to them — the sets cross, so per-term is not a preference but the only shape that fits. **`cookie` is already answered 5-to-1 inside our own tree**: in `th, ms, ar, tr, ko` all four siblings that ship the locale use the native word and VALO Tech alone ships Latin, and `assets/legal-i18n.js` sides with the siblings. **One file per locale under `docs/glossary/` (`I18N-001/T5`)**, keys `concept`/`preferred`/`forbidden` plus `basis` and `sources`, because Farola ships eight locales and PCE none and a twenty-locale file is unadoptable by both. **The trap to avoid**: VALOAds' `hi/ar/bn/ja/tr/ko` and Verdiq's sixteen non-priority locales are English seeds with decision entries saying so, and harvesting them would freeze untranslated state into the glossary as though somebody had chosen it. What the glossary then settles, and this row closes against: `assets/i18n.js`'s header sentence, which binds product names and technical terms as one class and honours it for the first while breaking it for the second; and the mismatch `SITE-006/T1` shipped, where a `tr` or `ko` reader meets a footer link labelled `Cookie` and opens a page headed `Çerezler` or `쿠키`.
  Refer to: SITE-006/T1 — the legal pages whose natural-word renderings the glossary is expected to ratify rather than overturn.

## REVIEW · Findings

- [x] REVIEW/T1 — Two test runs at once destroy each other’s isolated database, which surfaces as a timeout in whichever files they share
  Impact to: — none — the test harness itself (apps/web/vitest.config.mts), which no design owns and every feature’s evidence rests on.
  Evidence: **found by a controlled experiment, after four hypotheses of mine were measured and refused.** The symptom was a suite that passed file by file and failed a different handful in aggregate, across five full runs, every failure a timeout and not one an assertion. The cause is that each database-backed file owns a database named by a fixed constant and drops it in beforeAll with WITH (FORCE), which terminates whatever is connected — so a second vitest invocation pulls the first one’s database out from under it mid-test. **The experiment**: a full run alone is green at 65 files and 1149 tests; the same run with a second invocation of three of its files alongside failed exactly the files the two shared (apps/web/src/content/content-serve.test.ts and apps/web/src/content/content-stream.test.ts), and nothing else. I caused every red run in the record by overlapping invocations, and then mis-attributed it three times. **The four refutations are kept because each narrows a future search**: not a cold database connection (apps/web/src/ops/logger.test.ts opens none and fails the same way); not a cold filesystem cache (a cold start does cost about forty times a warm one, 6569ms against 149ms, but the next warm run failed worse); not the migrations (0.86s to apply every one to a fresh database); and not contention between the twenty-six per-suite databases (one drop and create 0.52s, four concurrently 1.33s, eight concurrently 2.86s, so all twenty-six cost under ten seconds). **What shipped**: the constraint is written into apps/web/vitest.config.mts beside the worker cap it belongs with, because the fixed name is the right trade — a per-run name would leak a database on every run, the drop being at setup rather than teardown — so this is a rule to know rather than something to engineer around. The per-test timeout also moves from vitest’s default five seconds to twenty, which is a separate and smaller point with its own measurement rather than a fix for this: a test that legitimately took 6569ms cold would fail a five-second limit on a machine also serving three development servers, and twenty seconds is three times the slowest honest reading while staying a sixth of the hook budget these files already declare, so a genuine hang still fails and fails quickly enough to read.
